# Building and tools

Everything is driven by one `Makefile` at the root of the repository. This page covers what you need installed, the `make` targets, where the build puts its files, how to switch compilers and flags, sanitizers, Windows, and the small tools that print what each compiler stage produced.

## Requirements

- A C11 compiler. The build uses `cc` unless you pick another one with `CC`.
- Flex, which generates the scanner from `compiler/frontend/lexer/scanner.l`.
- GNU Make and `ar`.
- Python 3.9 or later, for the test runners and repository checks.
- Git, which the repository checks call.

On macOS, `xcode-select --install` installs the Command Line Tools, which include all of these. On Debian or Ubuntu, run `sudo apt install build-essential flex python3 git`. On Fedora, run `sudo dnf install gcc make flex python3 git`.

## Make targets

| Command | What it does |
| --- | --- |
| `make` | Builds the six libraries, `ruvac`, every C test suite and every inspection tool |
| `make compiler` | Builds only `ruvac` and the runtime library |
| `make test` | Runs the repository checks and then every test suite |
| `make test-programs` | Runs every test suite without the repository checks |
| `make check-repository` | Runs only the layout and ignore-rule checks |
| `make sanitize` | Rebuilds in `build/sanitize` with AddressSanitizer and UBSan and runs the C suites, fixtures and integration tests |
| `make clean` | Deletes the whole `build` folder |
| `make windows-build` | Builds the Windows compiler, tests and tools (MSYS2 UCRT64 only) |
| `make windows-test` | Builds for Windows and runs `scripts/windows/verify.py` |

There is also one target per suite, such as `make test-parser` or `make test-native`. [Testing](testing.md#the-test-suites) lists them all. Building in parallel works as usual, for example `make -j8`.

## Build outputs

Everything goes under `build/debug` by default, and nothing is written into the source folders.

```text
build/debug/
  bin/ruvac                            the compiler
  lib/libruva_*.a                      foundation, lexer, parser, analysis, backend, runtime
  compiler/  runtime/  tests/          object (.o) and dependency (.d) files, mirroring the sources
  compiler/frontend/lexer/scanner.c    the scanner generated by Flex
  tests/<suite>/                       test programs and inspection tools
```

The test programs are `foundation-tests`, `lexer-tests`, `parser-tests`, `semantic-tests`, `runtime-tests`, `backend-tests` and `host-tests`, each in its own folder under `build/debug/tests/`. Object files track header dependencies, so after you edit a header `make` rebuilds only what depends on it.

To use the compiler from any folder, put its `bin` folder on your path:

```sh
export PATH="$PWD/build/debug/bin:$PATH"
```

## Choosing compilers, flags and the build folder

These variables can be set on the `make` command line:

| Variable | Default | Purpose |
| --- | --- | --- |
| `CC` | `cc` | C compiler for the build |
| `CFLAGS` | `-O0 -g` | Optimization and debug flags |
| `CPPFLAGS`, `LDFLAGS`, `LDLIBS` | empty | Extra preprocessor, linker and library flags |
| `BUILD_DIR` | `build/debug` | Where all outputs go |
| `SANITIZE_BUILD_DIR` | `build/sanitize` | Where `make sanitize` builds |
| `FLEX` | `flex` | Flex executable |
| `PYTHON` | `python3` | Python used by the test targets |

Give each setup its own `BUILD_DIR` so object files from different compilers or flags never mix:

```sh
make CC=clang BUILD_DIR=build/clang test
make CC=gcc BUILD_DIR=build/gcc CFLAGS="-O2 -g" test
```

The warning flags `-std=c11 -Wall -Wextra -Wpedantic -Werror` are always added on top of `CFLAGS`, so any warning stops the build. Do not add `-ffast-math`. `compiler/common/platform.h` rejects it on purpose, because Ruva's `real` arithmetic depends on strict floating-point rules.

`ruvac` itself reads `CC` from the environment when it builds a program, and falls back to `cc` (or `gcc` on Windows). `CC=clang ruvac main.ruv` builds that one program with Clang.

## Sanitizers

`make sanitize` rebuilds everything in `build/sanitize` with `-O1 -g -fno-omit-frame-pointer -fsanitize=address,undefined -fno-sanitize-recover=all`. It runs the seven C suites, every fixture set and the integration tests. It also sets `NATIVE_SANITIZE=1`, so the programs that `ruvac` builds during the native and integration tests get `--sanitize` too. Any memory error or undefined behavior fails the run. The repository checks and the Python unit tests for the tooling are not part of it.

To check a single program, add `--sanitize` when you compile it:

```sh
ruvac --sanitize main.ruv -o app
```

[Testing](testing.md#sanitizer-runs) shows how to run just one suite under sanitizers.

## Windows

A Windows x64 build with [MSYS2 UCRT64](https://www.msys2.org/docs/environments/) GCC is prepared, and its build and link checks pass. It has not been run on real Windows hardware yet, so reports from Windows users are very welcome. In the UCRT64 terminal:

```sh
pacman -S --needed make flex mingw-w64-ucrt-x86_64-gcc mingw-w64-ucrt-x86_64-python
make -j4 CC=gcc PYTHON=python BUILD_DIR=build/windows windows-test
```

This builds `build/windows/bin/ruvac.exe`. When the target compiler is MinGW, plain `make` means `windows-build` and `make test` means `windows-test`. That builds the compiler, the foundation, lexer, parser and host suites and the inspection tools. `verify.py` then runs them together with the fixtures, the module integration tests and the Windows tests in `tests/windows`. It writes `build/windows/verification.log` and `verification.json`, which are the files to attach to a report. Sanitizers are not available with this toolchain.

To copy a clean set of sources to a Windows machine, run `python3 scripts/windows/package.py`. It writes `build/windows/ruva-windows-source.zip` and a `.sha256` file next to it.

## Inspection tools

`make` builds a small tool for each front-end stage. Each takes one `.ruv` file and prints what that stage produced, or the stage's error with file, line and column.

| Tool | Flags | Prints |
| --- | --- | --- |
| `build/debug/tests/lexer/lexer-probe` | `--check` lexes without printing | One token per line as `line:column kind "spelling"`, with the decoded value after `->` for text literals |
| `build/debug/tests/parser/parser-probe` | `--module` parses the file as an imported module, `--check` parses without printing | The syntax tree as nested parentheses |
| `build/debug/tests/semantic/semantic-probe` | `--summary`, `--ast`, `--relative-diagnostics` | `modules=N symbols=N`, the checked tree of the entry file, and errors with paths relative to the current folder |

```sh
build/debug/tests/lexer/lexer-probe tests/fixtures/lexer/literals/input.ruv
build/debug/tests/parser/parser-probe --module examples/modules/model/item.ruv
build/debug/tests/semantic/semantic-probe --summary tests/fixtures/semantic/imports/input.ruv
```

`semantic-probe` follows `bring` imports, just like `ruvac`. Two more tools exist only for fixtures: `fixture-probe` exercises the shared code in `compiler/common`, and `runtime-probe` triggers runtime errors by name.

`ruvac` has two inspection modes of its own. `ruvac --check main.ruv` runs every check without producing anything, and `ruvac --emit-c main.ruv -o main.c` writes the generated C so you can read it.

## Where the runtime comes from

`ruvac` compiles the runtime from source every time it builds a program. To find it, the driver starts at its own executable and walks up the folders until it finds a `runtime` folder that contains `ruva_runtime.h`. That is why `build/debug/bin/ruvac` finds the `runtime` folder of your checkout without any setup.

If you copy `ruvac` somewhere else, point `RUVA_RUNTIME_ROOT` at the `runtime` folder:

```sh
export RUVA_RUNTIME_ROOT="$HOME/src/Ruva/runtime"
```

Keep that folder inside a full checkout, because the runtime build also uses a few files from `compiler/common/host` next to it. When the variable is set, `ruvac` uses only that path. If it is wrong, every build fails with `cannot locate runtime sources`.
